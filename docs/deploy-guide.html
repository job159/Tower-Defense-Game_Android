02為什麼要這樣部署

這套做法背後有五個原則，每個決定都能對應到其中之一。

原則 1

秘密只留在本機

簽署金鑰就是 App 的「身分證」。它一旦外流，別人就能冒充你發佈「更新」；它一旦遺失，你自己也再也無法更新已安裝的 App。所以金鑰不上傳 GitHub、不放雲端機器人，APK 一律在你的電腦簽好才上傳。

原則 2

能自動的都自動

網頁版和下載頁不需要任何秘密，就交給 GitHub Actions：每次 git push 自動重建、自動上線。你不用手動上傳網站檔案，也不會忘記更新。

原則 3

永久網址不綁版本

QR 碼指向「下載頁」而不是某個 APK 檔；下載頁的按鈕用 releases/latest/download/…，GitHub 會自動導向最新版本。出新版時什麼網址都不用改，舊的 QR 碼照樣有效。

原則 4

免費、可靠、不會過期

GitHub Pages 與 Releases 對公開專案完全免費、沒有到期日、全程 HTTPS、有全球 CDN，不需要自己維護伺服器，電腦也不必開著。只要 repo 還在，連結就一直有效。

原則 5

一個地方管全部、任何人都能重現

原始碼、版本紀錄、網站、安裝檔都在同一個 GitHub 專案裡。建置步驟寫成腳本與工作流程，別人 fork 後照著做就能得到一樣的結果（他們會自動產生自己的金鑰）。

附帶

保留「不安裝也能玩」的退路

網頁版和下載頁一起部署。如果某天手機不允許側載安裝、或朋友用 iPhone／電腦，打開 /play/ 就能直接玩。

03方案比較

「讓任何人掃碼下載 APK」有很多種做法。這張表說明為什麼選 GitHub Pages ＋ Releases。

方案任何網路長期有效費用電腦要開著缺點
區網伺服器（npm run serve，之前用的）只限同一個 Wi-Fi關機就沒了免費要只適合開發測試
雲端硬碟／網盤分享連結可以可能被停用或判定可疑免費不用每次新版都要換連結、APK 常被警告、無法自動化
自己租伺服器（VPS）可以要持續付費續約每月付費不用要自己維護安全更新、網域與憑證
Google Play 上架可以可以開發者帳號 US$25（一次）不用需要審核、隱私政策與測試者規定，流程最正式也最繁瑣
GitHub Pages ＋ Releases（現在的做法）可以repo 在就有效免費不用仍屬「側載安裝」，需允許未知來源（見第 9 節的 Google 新規）
為什麼 APK 放 Releases，而不是直接放進程式碼或網站？

APK 是二進位檔，每版都放進 git 會讓版本庫越來越肥大；Releases 是 GitHub 專門給「成品檔案」用的空間：每個版本各自保存、可以寫更新說明，還有 latest 這個永久捷徑。

04每個零件是什麼

部署裡出現的工具，用白話說明各自的角色。

版本控制

Git

記錄程式碼每一次變化的工具。每個「commit」是一張快照，可以隨時回到任何版本。你的電腦上原本就有安裝。

雲端版本庫

GitHub 儲存庫（repo）

放在 GitHub 上的 Git 版本庫：job159/Tower-Defense-Game_Android。公開、MIT 授權，任何人都能看、下載、fork。

自動化

GitHub Actions

GitHub 提供的雲端機器人。依照 .github/workflows/pages.yml 這份「工作流程」，每次推送就開一台 Linux 虛擬機自動建置網站。

網站主機

GitHub Pages

免費的靜態網站主機，網址是 帳號.github.io/專案名/。這裡放下載頁與網頁版遊戲，全程 HTTPS 並有全球 CDN 加速。

成品倉庫

GitHub Releases

存放每個版本的 APK（例如 v2.1.0）。/releases/latest/download/NeonBastion.apk 會自動導向最新一版。

指令工具

GitHub CLI（gh）

在終端機操作 GitHub 的官方工具：登入、開啟 Pages、建立 Release、上傳 APK、查看自動部署結果。安裝在 C:\Program Files\GitHub CLI\gh.exe。

身分證

簽署金鑰（keystore）

android/keystore/release.jks 與 keystore.properties。Android 只接受「同一把金鑰簽署」的更新，所以它決定了你能不能覆蓋安裝新版。只存在你的電腦。

入口

QR 碼與下載頁

QR 碼（docs/download-qr.png）裡只寫了下載頁網址。下載頁會即時向 GitHub 查詢最新版本號與檔案大小，並提供安裝步驟與網頁版入口。

05我做了哪些事（一次性設定）

以下是這次實際執行的步驟，照順序排列。標籤說明是誰做的：Claude 你 GitHub 自動

  1. 檢查環境 Claude

    確認電腦已有 Git，但沒有 GitHub CLI；也發現你的全域 git email 是真實信箱——公開 repo 裡每個 commit 都看得到它，所以後面改用隱私地址。

  2. 安裝 GitHub CLI Claude

    用 Windows 內建的 winget 從官方來源安裝（會驗證安裝檔雜湊值）。

    POWERSHELL
    winget install --id GitHub.cli -e --source winget
  3. 登入 GitHub 你

    這一步只能由你做：程式不能代你輸入帳密。指令會產生一次性代碼，你在瀏覽器輸入並授權，GitHub 發給這台電腦一張「通行證」（token），存在 Windows 認證管理員裡。

    POWERSHELL
    & "C:\Program Files\GitHub CLI\gh.exe" auth login --hostname github.com --git-protocol https --web
    為什麼用 --web 裝置授權？

    密碼從頭到尾只在 GitHub 官網輸入；這台電腦只拿到權限有限、可以隨時撤銷的 token（本次權限：repo、workflow、read:org、gist）。

  4. 整理專案，決定「什麼能公開」 Claude
    • .gitignore：排除 node_modules/（可重新安裝）、dist/ 與 build/（建置產物）、簽署金鑰（android/keystore/、*.jks、keystore.properties）、*.apk、本機工具設定 .claude/。
    • .gitattributes：統一換行字元，避免 Windows（CRLF）與 GitHub 的 Linux 機器（LF）互相打架。
    • LICENSE：MIT 授權全文。
    • package.json：加上 homepage、repository、license，以及 build:site、release 兩個新指令。
    • 掃描所有原始碼，確認沒有密碼、token、個人 email 或私人路徑。
  5. 寫好三支部署腳本 Claude
    • scripts/build-site.mjs：產生公開下載頁＋網頁版到 dist/site/。
    • .github/workflows/pages.yml：告訴 GitHub Actions 每次推送時怎麼建置與部署。
    • scripts/release.mjs：把本機簽好的 APK 發佈成 GitHub Release。

    另外把區網伺服器與公開下載頁共用的外觀抽到 scripts/site-common.mjs，兩個頁面長得一樣，只需要維護一份。

  6. 在本機測試網站 Claude

    用一個模擬 GitHub Pages 子路徑（/Tower-Defense-Game_Android/）的本機伺服器，確認下載頁在手機尺寸正常顯示、網頁版能在子路徑下啟動、沒有 Release 時按鈕會顯示「APK 準備中」。

  7. 建立本機版本庫並提交 Claude
    BASH
    git init -b main
git config user.email "<帳號ID>+job159@users.noreply.github.com"   # 只對這個專案生效
git add -A
git commit -m "霓虹防線 NEON BASTION v2.1.0"

    提交前再次確認：59 個檔案中沒有金鑰、APK、node_modules 或建置產物。

  8. 開啟 GitHub Pages（Actions 模式） Claude
    BASH
    gh api -X POST repos/job159/Tower-Defense-Game_Android/pages -f build_type=workflow

    「workflow」模式代表網站內容由 Actions 建置後上傳，而不是直接把某個分支的檔案原樣公開——這樣 repo 裡只需要放原始碼，不必提交建置產物。

  9. 推送到 GitHub Claude
    BASH
    git remote add origin https://github.com/job159/Tower-Defense-Game_Android.git

  10. 自動建置與部署網站 GitHub 自動

    推送觸發 pages.yml：安裝套件 → 建置網頁版 → 產生下載頁 → 上傳 → 部署到 Pages。這次整個流程約一分鐘完成。

  11. 發佈 APK Claude

    建立 Release v2.1.0 並附上本機簽署的 NeonBastion.apk（305 KB）。

  12. 從外部網路驗證 Claude

06以後怎麼出新版

四個步驟。在專案資料夾 C:\code\phone\app1 開終端機執行。

  1. 改版本號

    打開 package.json，把 "version" 改大，例如 2.1.0 → 2.1.1。

    版本號規則

    Android 內部版本 versionCode = 主版號×10000 ＋ 次版號×100 ＋ 修訂號（2.1.1 → 20101）。所以次版號與修訂號都必須 ≤ 99；而且新版必須比手機上的舊版大，否則無法覆蓋安裝。

  2. 建置（網頁版＋簽署 APK）
    POWERSHELL
    npm run build
  3. 提交並推送原始碼 → 網站自動更新
    POWERSHELL
    git add -A
git commit -m "v2.1.1：更新內容"
git push
  4. 發佈 APK → 下載頁自動指向新版
    POWERSHELL
    npm run release -- --notes "v2.1.1 更新內容"

    若同一個版本號已經發佈過，這個指令會改成「替換 APK」而不是新建。

推送後大約會發生什麼

0 秒git push 完成，GitHub 收到新 commit
約 5 秒Actions 啟動 Linux 機器，開始建置
約 1 分鐘網站部署完成，下載頁與網頁版更新
1～2 分鐘CDN 快取更新，全球都看到新版
release 後立即下載頁的按鈕改為新版 APK
手機端

玩家用同一個 QR 碼（或書籤）打開下載頁 → 下載 → 直接覆蓋安裝，遊戲進度會保留。

07每個指令背後發生什麼

npm run build = 建網頁版 ＋ 建 APK

① build:web（scripts/build-web.mjs）：用 esbuild 把 game/src/ 裡的所有 JavaScript（含 three.js）打包、壓縮成單一 game.js，連同 index.html、style.css 輸出到 dist/www/，並把版本號寫進遊戲。

② build:apk（scripts/build-apk.ps1）：不用 Android Studio／Gradle，直接呼叫 Android SDK 的工具：

步驟工具做什麼
1aapt2 compile / link編譯圖示、字串等資源，產生 AndroidManifest 與資源表
2javac編譯 WebView 外殼 MainActivity.java
3d8把 Java 位元碼轉成 Android 使用的 classes.dex
4打包把 dex 與 dist/www/ 網頁版放進 APK 的 assets/www/
5zipalign對齊檔案，讓 Android 能更快讀取
6apksigner用 🔒 android/keystore/ 的金鑰簽署並驗證 → dist/NeonBastion.apk

git push 觸發的 GitHub Actions（.github/workflows/pages.yml）

步驟動作為什麼
actions/checkout@v7下載 repo 的原始碼雲端機器是全新的空機器
actions/setup-node@v7安裝 Node.js 22建置腳本需要 Node
npm ci依照 package-lock.json 精確安裝套件每次建置用的套件版本完全一致
node scripts/build-web.mjs建網頁版與本機相同的建置流程
node scripts/build-site.mjs產生下載頁＋把網頁版放到 play/組成完整網站 dist/site/
configure-pages@v6
upload-pages-artifact@v5
deploy-pages@v5		上傳並部署到 PagesGitHub 官方的部署方式，只有這個流程有權限發佈網站

這個工作流程不會建 APK——雲端機器沒有你的金鑰，也不應該有。

npm run build:site（scripts/build-site.mjs）

  • 從 package.json 的 repository（或 Actions 提供的 GITHUB_REPOSITORY）算出網址。
  • 產生 index.html：下載按鈕連到 /releases/latest/download/NeonBastion.apk，並內嵌此頁網址的 QR 碼（電腦螢幕上才顯示，方便用手機掃）。
  • 頁面開啟時，瀏覽器向 api.github.com 查詢最新 Release，填入版本號、檔案大小、發佈日期；查不到時按鈕照樣能下載。
  • 複製 dist/www/ 到 play/，並產生網站圖示與 .nojekyll。

npm run release（scripts/release.mjs）

  • 讀取 package.json 的版本號 → 標籤 v2.1.1。
  • 確認 dist/NeonBastion.apk 存在，並找到 gh。
  • 如果這個標籤的 Release 還不存在：gh release create 建立並設為「最新版」；已存在就 gh release upload --clobber 替換 APK。

為什麼 latest/download 永遠是最新版？

這是 GitHub 內建的永久捷徑：/releases/latest/download/檔名 會被 GitHub 導向「標記為 Latest 的 Release」裡同名的檔案。只要每個版本的 APK 都叫 NeonBastion.apk，這個網址就不必變。

09安全與隱私

最重要：備份簽署金鑰

把整個 android/keystore/ 資料夾（release.jks ＋ keystore.properties）備份到至少兩個地方，例如隨身碟加上密碼管理器或私人雲端。遺失後果：所有已安裝的玩家都無法再更新，只能解除安裝（存檔會消失）後重裝。

也請不要把 keystore.properties 的內容貼到任何公開地方——它裡面有金鑰密碼。

已處理

金鑰不會被上傳

.gitignore 排除了金鑰資料夾、*.jks、keystore.properties；提交前也逐一檢查過檔案清單。雲端機器只建網頁版，不接觸金鑰。

已處理

真實 email 不公開

這個專案的 commit 使用 GitHub 隱私地址 帳號ID+job159@users.noreply.github.com（只對這個專案設定，其他專案不受影響）。

10疑難排解

下載頁沒有更新？

先看自動部署有沒有成功：GitHub 專案頁的 Actions 分頁，或用指令：

POWERSHELL
gh run list --workflow pages.yml --limit 5
gh run view --log-failed          # 看最近一次失敗的錯誤訊息
gh workflow run pages.yml         # 手動重新部署一次

成功後 CDN 可能還要 1～2 分鐘；手機瀏覽器可以重新整理或清除快取。

下載頁顯示「APK 準備中」？

代表還沒有任何 Release，執行 npm run release 即可。

下載頁只顯示「最新版」、沒有版本號？

GitHub API 對同一個網路每小時有查詢次數上限，暫時查不到時只是少了版本資訊，下載按鈕仍然正常。

手機說「應用程式未安裝」或無法覆蓋？

  • 新版本號沒有比手機上的大（見第 6 節的版本號規則）。
  • APK 用了不同的金鑰簽署（例如金鑰遺失後重新產生）——只能先解除安裝舊版。

終端機說找不到 gh？

剛安裝完的舊終端機不知道新路徑。關掉重開，或直接用完整路徑：& "C:\Program Files\GitHub CLI\gh.exe" …。npm run release 會自動找到它。

git push 被拒絕？

gh auth status        # 確認還在登入狀態、權限包含 repo 與 workflow
git pull --rebase     # 若在網頁上改過檔案，先把遠端的變更拉下來

11長期維護清單

✔ 不要改 repo 名稱、不要刪 repo

Pages 網址包含 repo 名稱，改名後網址會變，已印出去的 QR 碼就會失效（GitHub 不會幫 Pages 做轉址）。

✔ 金鑰至少兩份備份

換電腦時記得一起搬過去，放回 android/keystore/ 即可繼續用同一把金鑰發佈。

✔ 每個版本的 APK 都叫 NeonBastion.apk

latest/download 捷徑靠檔名對應；npm run release 已經固定用這個檔名。

✔ 偶爾看一下 Actions 是否成功

GitHub 會陸續更新雲端機器（例如 2026 年 10 月 ubuntu-latest 將升級到 Ubuntu 26）與官方動作版本；若某天部署失敗，通常只要把 pages.yml 裡的版本號改新即可。

✔ 換電腦重建環境

需要：Git、Node.js、GitHub CLI（登入一次）、JDK 17 與 Android SDK（建 APK 用），再 git clone 專案、npm ci、放回金鑰。

✔ 區網伺服器只是備用

npm run serve 仍可在同一個 Wi-Fi 下快速測試尚未發佈的版本；正式分享一律用公開下載頁。

12名詞小辭典

repo（儲存庫）
一個專案的所有檔案與版本歷史。
commit（提交）
一次變更的快照，附有說明文字與作者。
push（推送）
把本機的 commit 上傳到 GitHub。
branch main（主分支）
正式版本所在的分支；推送到 main 會觸發自動部署。
workflow（工作流程）
寫給 GitHub Actions 的自動化步驟清單（YAML 檔）。
Release（發佈版本）
附帶成品檔案（APK）與說明的正式版本，以 git 標籤（如 v2.1.0）標記。
CDN
分散在全球的快取伺服器，讓各地玩家都能快速載入網站。
HTTPS
加密連線，避免下載內容在傳輸途中被竄改。
APK
Android 的安裝檔。
簽署（signing）
用私密金鑰在 APK 上蓋章，證明它來自同一位開發者；Android 只接受同一把金鑰簽署的更新。
versionCode
Android 判斷新舊版本的整數；這個專案由版本號自動換算。
側載（sideload）
不透過 Google Play、直接安裝 APK。
token / scope
GitHub 發給工具的通行證與它的權限範圍，可隨時撤銷。
fork
把別人的公開 repo 複製一份到自己帳號下修改。
MIT 授權
最寬鬆的開源授權之一：可自由使用、修改、商用，只需保留著作權聲明。
